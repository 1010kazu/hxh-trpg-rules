# ルールブックの更新・検証・保存

保存先：[1010kazu/hxh-trpg-rules](https://github.com/1010kazu/hxh-trpg-rules)。公開リポジトリ、既定ブランチ `main`、リモート名 `origin`。すでに連携済みのため、Git初期化・リポジトリ作成は不要。

## 更新を始める

リポジトリのルートで実行する。

```bash
git status --short --branch
git remote -v
git fetch origin
git log --oneline --left-right HEAD...origin/main
```

作業中の変更と今回の変更を区別する。作業ツリーがきれいで、ローカルがリモートより遅れているだけなら `git pull --ff-only origin main` で取り込む。ローカルにも独自コミットがある場合は履歴を比較して統合する。未コミットの変更を勝手に破棄・退避せず、競合時も既存作業を保つ。強制pushで解消しない。

## 内容を更新する

[制作規約](../AGENTS.md)と[制作スキル](../skills/hxh-rulebook/SKILL.md)に従い、目的に応じて次を更新する。

| 更新する内容 | 合わせて確認する資料 |
|---|---|
| ルール本文 | 関連するシート、サンプル、早見表、シナリオ |
| 未定義の処理の補足 | [暫定補足台帳](supplements.md)と本文の定義箇所 |
| 数値・設計の変更案 | Issueに理由と影響を記録し、[調整課題](open-questions.md)へ対応付け、合意後に本文へ採用 |
| 章の移動・参照先の変更 | [原文対応表](source-map.md)と相対リンク |
| 検証・試遊の結果 | [検証記録](verification.md)、実卓で判明した課題 |
| 読者や制作者に影響する変更 | [変更履歴](changelog.md) |

保存原文 `sources/ver-0.2.md` は編集しない。`.gitattributes` は原文の改行を含むバイト保持とMarkdownの改行記法に合わせている。ファイルの追加・削除・改名時は、入口と参照元も更新する。

## Issueで検討・進捗を管理する

[Issue一覧](https://github.com/1010kazu/hxh-trpg-rules/issues)を議論と進捗の正本とし、現行ルールは本文の定義箇所へ残す。対応表は[暫定補足台帳](supplements.md)と[調整課題](open-questions.md)。台帳の確認実績や試遊ログは実施当時の記録であり、最新の進捗ラベルとは別に保持する。

- A番号：不足処理の暫定裁定の採否。Q番号：原文から継続する数値・バランスの評価。T番号：AI試遊で見つかった個別課題。同じ分野でも目的が異なれば別Issueにし、関連リンクを付ける。
- T01の距離問題はA12へ統合し、移動を扱うA17からも参照する。複数の論点を含む追加確認事項は、それぞれのA番号へ対応付ける。
- 番号は維持し、クローズ済みの番号を再利用・詰め直ししない。新規作成前に全状態のIssueを確認し、本文の管理ID（例：`<!-- rulebook-topic:A01 -->`）と対応表で重複を防ぐ。通信失敗で作成結果が不明な場合も、再取得して照合してから再開する。
- タイトルは `[A01] 時間単位の暫定裁定を検討する` の形式。本文に現行案と背景、決めたい点、AI試遊での観測、必要な検証ケース、完了条件、参照元・関連Issueを書く。公開済みの定義はPagesの該当アンカー、制作資料・試遊記録はGitHubのファイルへリンクする。GM資料へのリンクには秘密がある旨を明示する。

各Issueのラベルは次の3軸。標準ラベルは削除しない。種類は1つ、分野は1つ以上、状況は常に1つとし、進捗が変わったら古い状況ラベルを外す。新規Issueは「状況:検討待ち」、担当者・期限は指定がなければ未設定。

| 軸 | ラベル |
|---|---|
| 種類 | `種類:暫定補足`、`種類:バランス調整`、`種類:裁定整理` |
| 分野 | `分野:基本判定`、`分野:キャラ作成`、`分野:念・オーラ`、`分野:発`、`分野:戦闘`、`分野:装備`、`分野:負傷・回復`、`分野:成長`、`分野:GM・シナリオ` |
| 状況 | `状況:検討待ち`、`状況:検討中`、`状況:試遊待ち`、`状況:反映待ち`、`状況:完了` |

検討に着手したら「検討中」、案の評価に試遊が必要なら「試遊待ち」、合意済みの案を本文へ適用する段階なら「反映待ち」とする。試遊で問題が出たら検討中へ戻すなど、実際の状態に合わせる。GitHubのオープン／クローズとラベルの意味を一致させ、再検討で再オープンしたら状況ラベルも更新する。

採用する場合は、ユーザーとの合意、本文・台帳・関連資料への反映、機械検証と必要なAI模擬試遊を終え、結果と反映コミットをIssueに残す。その後「状況:完了」に置き換え、完了としてクローズする。見送る場合は理由を記録し、「状況:完了」に置き換え、見送り（not planned）としてクローズする。Issue作成や仮裁定だけでは採用済み・検証済みとしない。

## バージョン単位で検討・統合する

### 開始時の準備

1. 全状態のIssue・PR・マイルストーンと、直前の版の試遊記録・引き継ぎ課題を確認する。
2. 今回の版の全工程を記す管理Issueを最初に作成する。管理IDは `<!-- rulebook-topic:V04 -->` のように版を識別できる値とする。同じ管理IDがあれば既存の管理Issueを更新する。
3. 管理Issueの作成後に、`~v0.X` 形式のマイルストーンを作成する。例は `~v0.4`。同名の既存マイルストーンは再利用する。説明に管理Issueへのリンクと版の目的を記す。
4. 管理Issueと、その版で検討する全Issueを同じマイルストーンに紐づける。管理Issueには順序付きの対象一覧と依存関係を記す。単なる関連資料と、その版の完了対象を明示する。対象の追加・見送り・次版への移動は、下記の選定手順とユーザーの承認範囲に従い、理由を残して一覧とマイルストーンを更新する。

### 検討待ちIssueを対象へ取り込む

バージョン開始時、対象を見直すとき、全件検討後の統合へ進む前に、Openで「状況:検討待ち」のIssueを全件確認する。前版から引き継いだ課題に加えて、検討可能な課題をできるだけ今回のマイルストーンへ取り込み、実際に検討する。

- 最新本文・コメント・関連Issueを読み、判断に必要な資料、未解決の依存関係、既存の採用候補との関係を確認する。
- 前提がそろっている課題を追加する。前提課題も今回の版で検討できるなら、両方を追加して依存順に並べる。個別Issueの検討で前提が解消した場合は、保留した課題を再確認する。
- マイルストーンへ紐づけた課題は、管理Issueの対象一覧・検討順・依存関係にも追加する。追加理由と検討結果を記録する。関連リンクを置くだけで対象の検討を済ませた扱いにしない。
- 追加できない課題は、必要な資料・先行判断・検証環境などの具体的な保留理由と、再確認する条件を管理Issueへ記す。未着手や前版との直接の関連が薄いことだけを理由に除外しない。
- ユーザーが明示した対象外・延期・目的や完了条件を尊重する。この指示に基づく、承認範囲内で検討可能な課題の追加と検討は進めてよい。明示された範囲の変更が必要なら、理由と具体的な変更案を示して合意を得る。数値・設計の採否と本文反映は、それぞれの承認範囲に従う。

管理Issueには、確認した検討待ちIssue、追加した課題と理由、保留課題と再確認条件を残す。対象が増えたら検討済みチェックと統合前の確認対象にも反映する。次版の管理Issueを作成する際もこの選定方針を引き継ぎ、着手時に全件を再確認する。

GitHubのIssueが持てるマイルストーンは1つ。前版で完了した検討の再評価には、差分と新しい完了条件を記した次版課題を作成して元Issueを参照する。未完了の同一課題は既存Issueを再利用し、版を移した理由をコメントに残す。これにより完了済みの版の記録と継続課題の担当版を追跡できる。

### 個別Issueの検討

現行ルール、問題、現行維持を含む複数案と得失、具体例、採否の順で検討する。推奨案の採用や派生論点の判断をユーザーから委任されている場合は、その範囲で最後まで進める。結論、理由、未確定事項、関連Issueへの影響、検証実績と残る検証を各Issueへ記録する。

個別Issueは検討を終えた時点で管理Issueの「検討済み」にチェックする。本文反映や試遊が必要なら、Issue自体はその工程の完了までOpenで管理する。採用候補への合意と正式採用・本文反映の承認は別に記録し、既に与えられた承認は引き継ぐ。

### 全件の検討後

1. 管理Issueを読み直し、対象全件の検討結果、採用候補間の矛盾、延期した課題と理由を確認する。検討待ちIssueを再確認し、新たに検討可能になったものを追加してから全件の検討完了を確認する。
2. 採用の承認範囲を確認し、本文を統合する。版ごとの本文を別ファイルとして作成し、章・サンプル・発シート・早見表・シナリオ・用語・原文対応・台帳・変更履歴をそろえる。
3. 境界ケースと計算例を確認し、導入シナリオを終了・回復・成長までAI模擬試遊する。通し試遊に戦闘がなければ独立した場面で戦闘を補い、状態を混ぜない。対象コミットと差分、宣言・出目・資源・裁定・結論・未検証範囲を保存する。
4. 原文ハッシュ・対応先・リンク・サンプル数値、回帰テストと必要なサイト検証を実施する。内容を変更したら影響範囲を再確認し、最終差分に対応する記録を残す。
5. 見つかった問題点を次版以降のIssueへ対応付ける。観測、影響、改善候補、完了条件、発見元の版・記録・関連Issueを記載する。既存の同一課題があれば更新し、二重作成しない。進行不能や現版の成立を妨げる問題は、現版の未完了事項として解消またはユーザーと扱いを合意する。
6. 実際の継続課題がある場合は、次版の全工程を記す管理Issueを作成し、その後に次版の `~v0.X` マイルストーンを作成する。次版の管理Issueと引き継ぎ課題を紐づけ、前後の管理Issueを相互参照する。次版の対象・検討順は引き継ぎ時点の計画として示し、着手時に再確認する。さらに先の版への課題は対応予定版を明記する。
7. PR（MR）を作成し、反映コミットの同期とCIを確認する。本文・関連資料・台帳への反映、必要な検証、引き継ぎを終えた個別Issueを完了として閉じる。見送りは理由を残して閉じる。
8. 管理IssueにPR、コミット、検証記録、後続Issueと次版の管理Issue・マイルストーン、または後続課題がなく次版作成が不要との判断を記録する。全チェックと対象Issueの状態を確認して管理Issueを閉じ、マイルストーンを閉じる。マージ・公開は承認された範囲で実行する。

継続課題がない場合は、次版の管理Issue・マイルストーンを自動作成しない。管理Issueに「後続課題なし・次版作成不要」と確認日を記録し、現版のPR・CIと完了条件を満たして一区切りとする。実卓未検証・長期バランス未検証など確認範囲の限界は検証記録に残す。未検証というだけで空の次版を繰り返し作らず、具体的な問題・必要な検討が見つかった時点で既存の全状態を照合して次版の管理Issueを作る。

継続課題を次版へ引き継ぐ場合は、その版の管理Issueとマイルストーンまで用意する。その次の版の作成要否は、次版の統合・試遊時に判断する。

### 管理Issueの記載項目

以下の項目をその版の内容で埋める。Issueには種類1つ・分野1つ以上・状況1つのラベルを設定する。新規は検討待ちとし、着手時に検討中へ更新する。

- 管理ID、版、目的、前版の管理Issueと試遊記録
- マイルストーン名とURL（作成後に追記）
- 対象Issueの順序付き一覧、依存関係、各Issueの検討済みチェック
- 検討待ち全件の確認結果、追加対象と理由、保留課題と再確認条件
- 関連する参照Issue、対象外・延期の課題と理由
- 採用候補と正式採用・本文反映の承認記録
- 本文・関連資料の統合チェック
- 境界確認と導入シナリオの終了・回復・成長までのAI試遊チェック
- 機械検証・回帰・サイト検証と未検証事項のチェック
- 発見した問題の次版以降のIssue化と重複照合のチェック
- 継続課題があれば次版の管理Issue・マイルストーン作成と紐づけ、なければ次版作成不要の判断記録チェック
- PR作成・保存コミット・同期・CI確認のチェック
- 個別Issueの完了処理と管理Issue・マイルストーンの終了チェック

## 検証してコミットする

```bash
python3 scripts/validate.py
python3 -m unittest discover -s tests -v
git diff --check
git diff --stat
git diff
```

検証対象には原文ハッシュと55節の対応先、相対リンク、補足台帳、現行本文の定義に基づくサンプル数値、計算例が含まれる。原文と改訂後の本文の文章一致は要求しない。本文の初期値や計算式を読み取れない場合は失敗するため、定義の書式を変更したときは読み取り処理と回帰テストも更新する。関連するプレイ手順も読み直し、何を確認し、何が未確認かを検証記録に残す。実卓テスト・AI模擬試遊・机上確認を区別する。制作スキルを変更した場合は、利用可能なら skill-creator の `quick_validate.py` でも検証する。

今回変更したファイルを指定して登録する。以下は判定ルールを変更した場合の例であり、実際の対象に合わせて置き換える。新規ファイル・削除したファイルも対象に含める。

```bash
git add -- rules/02-checks.md design/changelog.md design/verification.md
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "docs: clarify opposed check rules"
```

他の作業者の変更や認証ファイルを混ぜない。コミットメッセージは変更の目的が分かる内容にする。変更がない場合は空のコミットを作らない。

## 閲覧サイトの更新・検証

サイトは `web/site.json` の明示リストから生成する。掲載対象はルール本文・プレイ資料・GM向けシナリオと [二次創作・権利表記](../NOTICE.md)。制作資料・AI試遊記録・保存原文・制作規約やスキルは含めない。正本のMarkdownを編集し、サイト用に本文を複製して管理しない。

初回は `python3 -m venv .venv` と `.venv/bin/python -m pip install -r web/requirements.txt` でサイトのビルド依存を用意する。本文の検証と既存の回帰テストは引き続きPython標準ライブラリだけで実行できる。

```bash
.venv/bin/python -m unittest discover -s tests/site -v
.venv/bin/python scripts/build_site.py
.venv/bin/python -m http.server 8000 --bind 127.0.0.1 --directory _site
```

ブラウザで `http://127.0.0.1:8000/` を開く。終了はCtrl+C。生成先は空フォルダのみを受け付ける。再ビルドは生成物のみの `_site` を削除するか、`--output` で別の空フォルダを指定する。生成物と仮想環境はGitへ登録しない。

サイトのビルドは既存アンカー・Markdown内リンクをHTML用に変換し、生成後の全ローカルリンク・資産・アンカーを検証する。掲載対象外のリンクは参照先を出さずにラベルのみを表示する。検索はサイト内のデータだけを使い、GMの秘密はチェックを入れた場合のみ検索する。GMページにはネタバレの注意を表示する。これは読み分けの補助であり、アクセス制限ではない。

サイトの変更では8件のサイトテスト、必要なブラウザ操作確認も実施する。本文の表示形式だけを変え、ルールの処理を変えない場合はAI模擬試遊の再実施は不要。掲載内容と機械検証だけでは確認できない日本語の読みやすさも確認する。

## GitHub Pagesの公開運用

公開サイト：[HUNTER×HUNTER TRPG](https://1010kazu.github.io/hxh-trpg-rules/)。ユーザーの指示により元のリポジトリを公開へ変更し、Pagesの配信元をGitHub Actionsに設定した。`PAGES_ENABLED=true` で [公開ワークフロー](../.github/workflows/pages.yml)が有効。mainへのpush時に検証・ビルド・再公開する。

GitHubのリポジトリでは制作資料・試遊記録・保存原文も閲覧できるが、Pagesには `web/site.json` の19ページだけを掲載する。この区別は今後の更新でも維持する。権利表記は [NOTICE](../NOTICE.md)を正本とする。

保存後は通常の検証に加え、公開ワークフローの対象コミットが成功したことを確認し、サイトのトップ・章・検索データを取得できること、権利表記とGM資料の注意が表示されることを確認する。

```bash
gh run list --workflow pages.yml --commit "$(git rev-parse HEAD)"
gh run watch RUN_ID --exit-status
gh api repos/1010kazu/hxh-trpg-rules/pages --jq '{html_url,public,build_type,https_enforced}'
```

`RUN_ID` は対象コミットの公開実行IDに置き換える。設定は `public: true`、`build_type: workflow`、`https_enforced: true` を期待する。初期化・Pages再作成は不要。必要な場合の再実行は `gh workflow run pages.yml --ref main` を使う。

公開停止や公開範囲の変更はユーザーの指示に従う。`PAGES_ENABLED` の解除だけでは既存サイトは消えないため、以降のデプロイ無効化とPages自体の停止を区別する。デプロイに失敗した場合は直前の公開版と今回の未反映コミットを区別して報告する。

## AIによる模擬試遊

ルールの処理・数値・発や装備の性能を変更する場合は、コミット前に変更箇所の境界ケース確認と、導入シナリオ1回の通し試遊を実施する。誤字修正・運用資料のみの変更は対象外。ゲーム進行スクリプトやGitHub Actionsで代行せず、この制作作業を担当するAIが実行する。

1. [試遊テンプレート](playtests/template.md)を `design/playtests/YYYY-MM-DD-内容.md` に複製し、対象コミット・未コミット差分・使用シナリオとPC・変更点を記す。同日複数回は末尾に連番を付ける。
2. 初期状態を定め、GMだけの秘密とPCが獲得済みの情報を分けて進行する。行動・対象・対応・補正を決めた後に乱数ツールで振り、出目を採用する。計算補助は可、ゲームの判断・進行・評価はAIが行う。
3. 主要な判定と、オーラ・拘束・配分・負傷・行動回数の変化を記録し、結末・回復・成長まで進める。戦闘がなければ別場面で補い、その状態を通し試遊へ混ぜない。
4. 未定義の処理は記録する。仮裁定で進めるなら先に条件を明示する。続行不能なら停止地点を残す。境界条件を狙った指定出目の確認は、通常の乱数試遊と区別する。
5. 「確認範囲で問題なし／要調整／進行不能」で結論を残し、発見をIssueへ記録し、[調整課題](open-questions.md)に対応付ける。数値・既存設計の変更は相談後に採用。最終稿でルールが再変更されたら試遊も再確認する。

[初回記録・GM用の秘密あり](playtests/2026-10-18-ver-0.2-baseline.md)を形式の例にできる。人間の実卓テストは別に記録し、AIの確認だけで楽しさ・全体バランス・人間の所要時間を保証しない。

## GitHubへ保存し、同期を確認する

```bash
git push origin main
git status --short --branch
git rev-parse HEAD
git ls-remote origin refs/heads/main
gh repo view 1010kazu/hxh-trpg-rules --json nameWithOwner,isPrivate,defaultBranchRef
```

ローカルHEADとリモートmainのハッシュ一致、保存先名、`isPrivate: false`、既定ブランチ `main` を確認する。今回の変更が残っていないことも確認する。他の作業者の未コミット変更がある場合は、それを残したまま区別して報告する。

このリポジトリで依頼された更新は、ユーザーから別の指定がなければ、検証・コミット・push・同期確認まで行う。報告には変更内容、検証結果、コミット、保存状況を含める。pushに失敗した場合はローカルのコミットを残し、未保存であることと原因を伝える。

## GitHub Actionsの結果を確認する

[検証ワークフロー](../.github/workflows/validate.yml)はpush、main宛てのPR、手動実行で起動し、Python 3.12で検証スクリプトと回帰テストを実行する。追加の秘密鍵やAI APIは使わない。ローカルはPython 3.8以上・標準ライブラリで実行可能。Actionsには読み取り権限だけを与える。

```bash
gh run list --workflow validate.yml --commit "$(git rev-parse HEAD)"
gh run view RUN_ID --exit-status
```

`RUN_ID` は対象コミットの実行IDに置き換える。待機中なら `gh run watch RUN_ID --exit-status` で結果を確認する。失敗したらログを調べ、関連箇所を修正・再検証して保存する。実行自体が無効化されている場合は、ローカル検証結果とCI未確認を分けて報告する。AI模擬試遊の実施・妥当性はCIの合格では証明できず、記録をAIが確認する。

## 認証・権限・競合で止まった場合

まずエラーを読み、認証不備、ネットワーク制限、Git管理領域の書き込み制限、リモートとの競合を区別する。実行環境の制限であれば、必要なコマンドを承認付きで再実行する。サンドボックス内の接続失敗だけで認証切れと判断しない。

通常の端末でも認証に失敗する場合に限り、以下で確認・再ログインする。

```bash
gh auth status
gh auth login --hostname github.com --git-protocol https --web
gh auth switch --hostname github.com --user 1010kazu
gh api user --jq .login
```

pushがリモートの更新で拒否された場合はfetchして差分を確認し、既存の変更と統合して再検証する。既存リポジトリの再作成や履歴の強制上書きは行わない。

## 現行版の通読本文

章別の `rules/01`〜`10` を定義の編集先とし、`rules/ver-0.X.md` の現行版は同じ内容を章順にまとめる。更新時は見出しを1段下げ、通読内のアンカーへ章ファイル名の接頭辞を付ける。章への相対参照を保持してから全体検証する。公開範囲は `web/site.json` の明示リストで確認する。

過去版の通読本文は当時の記録として保持し、現行章から新しい版の通読本文を作成する。入口は現行版へ更新する。
