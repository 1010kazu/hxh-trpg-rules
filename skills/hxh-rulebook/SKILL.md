# HUNTER×HUNTER TRPG 制作

リポジトリルートはこのファイルから `../..`。[制作規約](../../AGENTS.md)を適用する。[入口](../../README.md)で読者向けの導線を確認する。

## 章の執筆・改訂

対象章と[原文対応](../../design/source-map.md)から原文を照合する。重複記述を増やす前に定義元を選び、手順→必要な判定→結果の順に初心者が追えるよう書く。出典のない処理をVer.0.2の確定事項として書かない。

不足処理は[暫定補足台帳](../../design/supplements.md)の未使用番号を取り、本文に「暫定補足 Axx」として定義し、理由・影響・確認状況を台帳に残す。既存数値・設計の変更は[調整課題](../../design/open-questions.md)で提案し、ユーザーの指示・合意がある場合に反映する。

## 発の設計レビュー

[発の作成](../../rules/05-hatsu.md)と[発シート](../../play/hatsu-sheet.md)を使う。能力原理からの自然な応用を無料のまま保ち、独立効果を区別する。構築値は最大性能、消費は実使用性能で計算する。適性は使用系統ごとに1回、共通の射程等は二重計上しない。

主効果・副効果、強度、射程、対象、持続、特殊性、適性を別記し、取得合計が容量以内か確認する。制約で構築値を引かない。行動・命中・抵抗・成立結果・維持・終了・反復の追加消費を合意事項として明文化する。持続を返金可能な無限攻撃・治療にしない。防御等の未定義カテゴリは強度だけから数値式を作らず個別裁定を記載する。

## 整合性確認

資源の点数と配分の段階、負傷値と累積負傷点を分けて追跡する。流・堅・硬・隠のタイミングを1ラウンドの例で確認する。基本値・上限・同値と特殊出目の優先順位を確認する。

`python3 scripts/validate.py` と `python3 -m unittest discover -s tests -v` をルートで実行し、関連するサンプル・早見表・導入シナリオも更新する。[検証記録](../../design/verification.md)に実施結果と実卓未確認を分けて残し、[変更履歴](../../design/changelog.md)に読者への影響を記す。

## AI模擬試遊

ルールの処理・数値・発や装備の性能を改訂したら、変更箇所の境界ケースと導入シナリオを1回、終了・成長まで試遊する。誤字修正や運用資料のみなら省略できる。[試遊テンプレート](../../design/playtests/template.md)を複製し、[初回記録・GM用の秘密あり](../../design/playtests/2026-10-18-ver-0.2-baseline.md)を記録例として使う。

AIがGMとPCの行動・裁定・評価を行い、ダイス生成と計算だけツールで補助する。対象・対応と補正を確定してから振り、都合で出目を選び直さない。境界を狙う指定出目ケースは乱数試遊と別記する。PCが得た情報とGMの秘密を分け、単一AIでの知識隔離の限界も残す。

対象コミットと未コミット差分、初期状態、各出目・計算・オーラ・配分・負傷の変化、結末・回復・成長を記録する。通し試遊で戦闘がなければ初期状態を戻した別場面で補う。裁定不足は仮裁定と明記し、進行不能なら停止と未検証範囲を記録する。

結論は「確認範囲で問題なし／要調整／進行不能」。改善案は調整課題へ記録し、数値・既存設計を合意なく変更しない。実卓の楽しさ・全体バランスを確認済みと扱わない。ルールを再変更した場合は影響箇所と通し試遊を再確認し、最終稿に対応する記録を残す。

## 閲覧サイトの確認

本文を変更したら、サイト用に複製せず正本からビルドする。[運用ガイド](../../design/workflow.md)のサイト検証手順を使い、公開範囲・変換後リンク・既存アンカーを確認する。GMの秘密は掲載対象、制作資料・試遊記録・原文は掲載対象外。権利表記は [NOTICE](../../NOTICE.md)を参照する。現在は公開保留のため、GitHubへの保存だけを行い、ユーザーの再開指示なしでPagesを有効化しない。

## 更新の保存

[運用ガイド](../../design/workflow.md)に沿って、作業前の状態確認から検証・関連差分のコミット・push・同期確認まで行う。ユーザーがローカル作業のみなど別の指定をした場合はそれを優先する。ファイルの削除や改名では入口・参照元を更新する。既存作業を保持し、保存できなかった場合はローカルとリモートの状態を分けて報告する。
